# 2x2x2 learned heuristic (DeepCubeA-style): exact evaluation

The shipped network [`weights/cube2/cube2-davi-v1.onnx`](../../weights/cube2/cube2-davi-v1.onnx)
(manifest: [`cube2-davi-v1.json`](../../weights/cube2/cube2-davi-v1.json)) is a cost-to-go
function trained with DAVI and used by batch weighted A* (BWAS). Both follow Agostinelli,
McAleer, Shmakov and Baldi, *Solving the Rubik's cube with deep reinforcement learning and
search*, Nature Machine Intelligence 1:356-363, 2019 [Ago19]. See
[`docs/theory/deepcubea.md`](../theory/deepcubea.md) for the method and
[`docs/training.md`](../training.md) for the workflow.

The 2x2x2 has only 3,674,160 states in the fixed `DBL` frame, so everything here is
measured against the **exact** distance table: the heuristic over every state, and the
solver against the true optimal length of each test state. There is no sampling error in
the heuristic numbers.

## Headline (default shipped setting: lambda = 0.6, batch N = 100)

| test set | n | solved | optimal | mean length | mean optimal | mean expanded | median expanded |
|---------|--:|-------:|--------:|------------:|-------------:|--------------:|----------------:|
| uniform random states | 1000 | 100.0% | 99.9% | 8.751 | 8.750 | 639 | 664 |
| stratified, up to 100 per depth 0-11 | 964 | 100.0% | 99.7% | 6.660 | 6.657 | 437 | 464 |

Every test state was solved. Non-optimal solutions were at most one move longer than optimal.
No `--max-expanded` limit was set. The network is **not admissible** (it overestimates
17.4% of states), so BWAS never reports these solutions as proven optimal (AGENTS.md
invariant 4). "Optimal" above means "length equal to the table distance".

## Setup

- Machine: 8 vCPU Intel Xeon (cloud VM), 31 GB RAM, Linux, **no GPU**. PyTorch 2.14.1
  (CPU), ONNX Runtime 1.23.2 (CPU, all cores, loaded at run time by `gpss-learn`).
- Encoding: `cube2/corner-cubie/v1`, 8 categorical features of 24 classes
  (`3 * cp[i] + co[i]`), generated by Rust (ADR 0008).
- Network: one-hot input -> 512 -> 256 -> 3 residual blocks (256) -> 1, ReLU + batch
  norm, 629,761 parameters, 2.5 MB ONNX (opset 18).
- DAVI: 400 updates of 100,000 fresh states scrambled 1-14 moves from the goal (40 M
  samples seen). 250 Adam steps of batch 1000 per update, lr 1e-3. The target network is
  synced when the loss falls below 0.05, or after 10 updates without a sync. That forced
  sync is a documented deviation from the paper (see `docs/training.md`): this small
  network plateaued near loss 0.15, which otherwise stalls the target at about depth 8.
  43 syncs in total, 35 of them forced. Wall time 1.70 h on the machine above, seed 1.
- Evaluation: `gpss evaluate --weights weights/cube2/cube2-davi-v1.json`, seed 1. The raw
  JSON is in [`data/`](data/) (`cube2-learned-main.json` plus one file per setting).

The network is accurate to about 0.1 moves up to depth 5, then saturates near 8. It
underestimates every state at depth 10 and 11 by about 2 and 3.4 moves. DAVI targets for the deepest

states at depth 10 and 11 are rare in 1-14-move random scrambles. A larger network, more updates
or a lower forced-sync budget would probably close this gap, but search does not need it
to (below).

What the sweep shows:

- **Batch size dominates.** With N >= 100, every lambda gives at least 99.9% optimal
  solutions at the same node count. With N = 1000, every lambda gives 100% at about 5,100
  nodes.
- **Small batches lean on the heuristic.** With N = 10, about 90 nodes are expanded
  (nearly the 9-move branching factor times the depth), and lambda trades length for
  nothing measurable here: 90% optimal at lambda 0.8, 72% at lambda 0.2 (up to 8 extra
  moves).
- With lambda = 1 and N = 1 this is plain A* with the learned heuristic: 39 nodes on
  average, 94% optimal, at most 1 extra move.
- For comparison, IDA* with the admissible dual PDB heuristic expands 943 nodes on average
  on the corpus `mid` bucket (depths 6-9) and 19,076 on `top` (depths 10-11)
  ([`cube2-gpss-bench.md`](cube2-gpss-bench.md)). It proves optimality; the learned
  search does not.

The CLI default (`--lambda 0.8 --batch-size 10`) favours few expansions. CI and the
headline above use `--lambda 0.6 --batch-size 100`, which favours solution length.

## Reproduce

```bash
cargo build --release -p gpss-cli --features learn
pip install -r training/requirements.txt          # provides ONNX Runtime
W=weights/cube2/cube2-davi-v1.json
./target/release/gpss evaluate --weights $W --lambda 0.6 --batch-size 100 > main.json   # ~1 min
./target/release/gpss evaluate --weights $W --lambda 0.8 --batch-size 10 --no-exhaustive > s.json
(cd training && python3 -m gpss_train report heuristic ../main.json)       # tables above

# Retrain from scratch (~1.7 h on 8 CPU cores); see docs/training.md
(cd training && python3 -m gpss_train train --run-dir runs/cube2-davi-v1 --updates 400 --seed 1)
```

Retraining with the same seed gives a statistically similar network, but not
bit-identical weights: PyTorch CPU kernels are multi-threaded, so floating-point
reductions are not deterministic.
